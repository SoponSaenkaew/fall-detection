วงจรฮาร์ดแวร์และตาราง Pinout (Hardware Schematics & Pinout)

รายละเอียดขา GPIO แรงดันไฟฟ้า วงจรรีเลย์ และปุ่มจำลองบนบอร์ด ESP32-S3

ESP32 Pin อุปกรณ์ที่เชื่อมต่อ ชนิดสัญญาณ (Mode) โปรโตคอล / ระดับลอจิก หน้าที่การทำงาน
GPIO 18 HLK-LD6002C (TX Pin) Digital INPUT (RX0) UART 115200 Baud รับ Binary Frames ตรวจจับคนหกล้มและพิกัด
GPIO 17 HLK-LD6002C (RX Pin) Digital OUTPUT (TX0) UART 115200 Baud ส่งคำสั่ง Config / Reset สู่โมดูล LD6002C
GPIO 16 HLK-LD2410C (OUT Pin) INPUT_PULLDOWN Active HIGH (3.3V) ตรวจสอบการมีคนอยู่ในห้อง (HIGH=มีคน, LOW=ห้องว่าง)
GPIO 15 Relay Module + Buzzer OUTPUT Active LOW (0V=ดัง) ขับเสียงไซเรนฉุกเฉินเมื่อเกิดเหตุล้ม (LOW=สับสวิตช์)
GPIO 48 WS2812B RGB LED OUTPUT NeoPixel 800kHz Single-wire ไฟบอกสถานะ (เขียว=ว่าง, น้ำเงิน=มีคน, แดง=ล้ม, ส้ม=อยู่นาน)
GPIO 4 Button: Sim Fall INPUT_PULLUP Active LOW (กดปุ่ม) ปุ่มทดสอบบนบอร์ด: บังคับเกิดเหตุล้มทันทีเพื่อสาธิต
GPIO 5 Button: Sim Enter INPUT_PULLUP Active LOW (กดปุ่ม) ปุ่มทดสอบบนบอร์ด: บังคับสถานะมีคนเข้าห้องน้ำ
GPIO 1 Button: Sim Exit INPUT_PULLUP Active LOW (กดปุ่ม) ปุ่มทดสอบบนบอร์ด: บังคับสถานะคนออกจากห้องน้ำ
5V & GND Power Supply Rails Power Input DC 5V / 2A Step-Down จ่ายไฟเลี้ยงเรดาร์ LD6002C, โมดูลรีเลย์ไซเรน และบอร์ด ESP32

ระบบจ่ายไฟและความเสถียร (Power Architecture)

เซนเซอร์เรดาร์ 60 GHz (LD6002C) มีช่วงพีคกระแสส่งคลื่นความถี่สูงถึง 400-500 mA การต่อไฟตรงจากขา 3.3V ของบอร์ดไมโครคอนโทรลเลอร์จะทำให้เกิดแรงดันตก (Voltage Drop) และทำให้บอร์ดรีสตาร์ทตัวเอง เราจึงใช้แหล่งจ่ายไฟ 5V 2A ภายนอก แยกรางจ่ายให้กับเรดาร์และรีเลย์โดยตรง พร้อมต่อ C ฟิลเตอร์ 100uF คร่อม VCC/GND

วงจรรีเลย์ Active LOW สำหรับไซเรน

โมดูลรีเลย์ที่ใช้เป็นแบบ Active LOW กล่าวคือเมื่อขา GPIO 15 จ่ายแรงดัน 0V (LOW) ทรานซิสเตอร์ออปโต้จะนำกระแส ทำให้ขดลวดรีเลย์สับสวิตช์ส่งเสียงไซเรน และเมื่อจ่าย HIGH (3.3V) รีเลย์จะตัดวงจร ดังนั้นในโค้ดฟังก์ชัน setup() จึงต้องสั่ง digitalWrite(RELAY_BUZZER_PIN, HIGH) ก่อนเสมอ เพื่อป้องกันเสียงดังรบกวนขณะเปิดเครื่อง

เจาะลึกโปรโตคอลเรดาร์ (Radar Protocols: LD6002C & LD2410C)

โครงสร้าง Binary Frame การคำนวณ Checksum และการประมวลผลข้อมูลระดับไบต์

HLK-LD6002C โครงสร้างเฟรมข้อมูล Binary (UART 115200 Baudrate)

เรดาร์ส่งข้อมูลเป็น Binary Stream ความเร็วสูง โดยแต่ละแพ็กเก็ตมีความยาวแปรผัน แต่มีโครงสร้างคงที่ 8 ไบต์แรก:

รหัสชนิดข้อความ (Message Types) ตามคู่มือทางการ HLK-LD6002C Communication Protocol: TinyFrame Standard
0x0E02 : MSG_IND_FALL_STATUS Radar → MCU

รายงานผลตรวจจับการล้ม: Payload 1 ไบต์ (0x01 = หกล้ม, 0x00 = ท่าทางปกติ)

0x0E0C : MSG_IND_FALL_SET_ALARM_AREA Two-way (16 Bytes)

กำหนดขอบเขตพื้นที่เตือนภัย / ขนาดห้อง: ส่ง Float 4 ค่า (rect_XL ซ้าย, rect_XR ขวา, rect_ZF หน้า, rect_ZB หลัง)

0x0E04 : MSG_IND_FALL_SET_HIGH Two-way (4 Bytes)

ตั้งค่าความสูงติดตั้งเรดาร์จากพื้น: ส่ง Float 4 ไบต์ (ระยะ 1.0 - 5.0 เมตร เช่น 2.2m) และเรดาร์ตอบรับ ACK (0=fail, 1=success)

0x0E08 : MSG_IND_FALL_SET_THRESHOLD Two-way (4 Bytes)

ตั้งค่าเกณฑ์ความสูงตัดสินการล้ม (Fall Threshold): Float 4 ไบต์ (ค่าเริ่มต้น 0.6m หรือปรับตั้ง 0.5m) และเรดาร์ตอบรับผล

0x0E0E : MSG_TARGET_HEIGHT Radar → MCU (Live)

รายงานระดับความสูงสดของเป้าหมาย: เรดาร์ส่งระดับความสูงของเป้าหมายจากพื้นแบบอัตโนมัติ (Float 4 ไบต์)

0x0E06 / 0x0E0A : GET_HIGH & SENSITIVITY Config Commands

0x0E06 อ่านค่าพารามิเตอร์ทั้งหมด 28 ไบต์ | 0x0E0A ตั้งค่าความไวตรวจจับ (3~10 เฟรม)

โค้ดการคำนวณ Checksum และถอดรหัสใน RadarSensors.h: ESP32 Firmware 
// สูตรคำนวณ Checksum ของ LD6002C: Bitwise Invert of XOR sum (~XOR)
uint8_t calcXor = 0;
for (int i = 0; i < frameLen - 1; i++) {
    calcXor ^= buffer[i];
}
uint8_t expectedChecksum = ~calcXor; // กลับบิตทั้งหมด

if (buffer[frameLen - 1] == expectedChecksum) {
    uint16_t msgType = (buffer[4] << 8) | buffer[5];
    if (msgType == 0x0E02) { // เฟรมตรวจจับการล้ม
        uint8_t isFall = buffer[6]; // ไบต์แรกของ Payload
        if (isFall == 0x01 && current_event != "exit") {
            triggerFallEvent(); // ยืนยันการล้ม (Sensor Fusion Guard)
        }
    }
}

ตรรกะการผสานข้อมูลเซนเซอร์ (Sensor Fusion & Edge State Machine)

อัลกอริทึมกรอง False Alarm, ระบบฟื้นตัวอัตโนมัติ (Recovery) และหน่วยความจำ NVS Flash

จุดอ่อนของระบบที่ใช้เรดาร์ตัวเดียวคือ False Alarm จากสิ่งของตกหล่น เช่น หากขวดแชมพูหรือผ้าเช็ดตัวร่วงหล่นลงพื้น คลื่นความถี่ 60GHz อาจตีความว่าเกิดการตกกระทบของมวล (Fall) ดังนั้นเราจึงออกแบบกลไก Sensor Fusion ข้ามย่านความถี่:

1. Empty Room Guard

แม้ LD6002C จะยิงเฟรม 0x0E02 (Fall) ออกมา แต่เฟิร์มแวร์จะไม่ประมวลผล หาก LD2410C รายงานว่าห้องว่าง (ขา OUT เป็น LOW) ทำให้ตัดปัญหาสิ่งของตกในห้องน้ำที่ไม่มีคนได้อย่างเด็ดขาด 100%

2. Fall Recovery & Failsafe

Auto Recovery: หากคนล้มแล้วพยุงตัวลุกขึ้นยืนทรงตัวได้เกิน 2.5 วินาที ระบบจะปรับจาก fall คืนสู่ enter
Failsafe: หากค้างสถานะล้มแต่คนเดินออกไปแล้วเกิน 20 วินาที จะตัดเข้า exit

3. Prolonged Stay (อยู่นาน)

เมื่อมีคนเข้าห้องน้ำ ตัวนับเวลาจะเริ่มเดิน หากอยู่ต่อเนื่องเกินเวลาที่ตั้งไว้ (ดีฟอลต์ 30 นาที) บอร์ดจะส่งเตือน prolonged_stay โดยปิดเสียงไซเรน (Silent Alert) เพื่อเคารพความเป็นส่วนตัวและไม่รบกวนผู้สูงอายุ

State (สถานะ) เงื่อนไขเซนเซอร์ ไฟ LED (WS2812B) รีเลย์ไซเรน (Relay) การแจ้งเตือนทาง LINE
exit ห้องว่าง LD2410 OUT = LOW (> 5 วินาที) 🟢 เขียวนิ่ง (Green) OFF (ขา 15 = HIGH) - ไม่ส่ง -
enter มีคนใช้งาน LD2410 OUT = HIGH (ตรวจพบคน) 🔵 ฟ้านิ่ง (Blue) OFF (ขา 15 = HIGH) - ไม่ส่ง -
fall คนล้มฉุกเฉิน! มีคน + LD6002C Frame 0x0E02 🔴 แดงกะพริบถี่ (Blink Red) 🔊 ON ดังต่อเนื่อง (ขา 15 = LOW) 🚨 แจ้งเหตุฉุกเฉินทันที!
prolonged_stay อยู่นานเกิน สถานะ enter ต่อเนื่อง ≥ timeout 🟠 ส้มนิ่ง (Orange) OFF (ปิดเสียงเพื่อความเป็นส่วนตัว) ⏳ ส่งแจ้งเตือนเคาะประตูห้อง
offline ขาดการเชื่อมต่อ MQTT Heartbeat ขาด / ไฟดับ (LWT) - (ตัวเครื่องดับ) - การ์ดแสดงสถานะสีเทาบนแดชบอร์ด
การบันทึกค่าลง Non-Volatile Storage (NVS Flash Memory)

เมื่อผู้ดูแลตั้งค่าความสูงเพดาน (Mount Height) หรือเวลาเตือนอยู่นาน (Stay Timeout) จากหน้าแดชบอร์ด ข้อมูลจะถูกส่งลงบอร์ดผ่าน MQTT และเซฟลงชิป ESP32 NVS Flash ทันที เมื่อไฟดับหรือดึงปลั๊กออก ค่าคอนฟิกเหล่านี้จะไม่สูญหาย และบอร์ดจะนำมาใช้ทำงานต่อได้ทันทีที่ไฟมา

โปรโตคอลการสื่อสาร MQTT, JSON Payload และกลไก LWT

การออกแบบ Topic, โครงสร้างข้อมูล JSON และการตรวจจับเครื่องดับฉับพลันด้วยพินัยกรรม

โครงสร้าง Topic ในระบบ

  • sensor/events
    บอร์ดส่ง Event ขึ้น Backend (fall, enter, exit, stay)
  • sensor/settings
    Backend ส่งคำสั่งปรับพารามิเตอร์ลงบอร์ด (Remote Config)

การใช้ MQTT QoS 0 ทำให้การส่งข้อมูลมี Overhead ต่ำเป็นพิเศษ (ไม่เกิน 200 ไบต์ต่อแพ็กเก็ต) รองรับการรับส่งผ่านเครือข่าย Wi-Fi ที่สัญญาณอ่อนในมุมอับของห้องน้ำได้ดี

4. สรุปเหตุผลเชิงสถาปัตยกรรมสำหรับตอบกรรมการ (Architectural Decision Records - ADR)

1 ทำไมต้องแยก `device_settings` ออกจาก `devices` (1:1)?

ตอบ: เป็นการทำ Table Normalization แยกความถี่ในการเข้าถึงข้อมูล (Separation by Access Frequency) ตาราง `devices` ถูกอ่านและอัปเดตสถานะแบบ High Frequency (เมื่อมีคนเข้า/ออก หรือ Heartbeat ส่งมา) หากรวมพารามิเตอร์ขนาดห้องไว้ในตารางเดียว ทุกครั้งที่ Update จะทำให้ขนาดของ WAL Log และ Buffer Cache ใหญ่โดยเปล่าประโยชน์ การแยกตารางทำให้ `devices` ทำงานได้เร็วและไม่เกิด Row Lock ไปยังคอนฟิกครับ

2 ทำไมผูก `notification_configs` กับ `groups` แทนที่จะผูกกับ `devices`?

ตอบ: อิงตาม Operational Workflow ในความเป็นจริง ครับ เจ้าหน้าที่พยาบาลหรือรปภ. จะเข้าเวรดูแลเป็น "อาคาร" หรือ "วอร์ด" หากอาคารมี 20 ห้องน้ำ การผูกระดับห้องน้ำจะทำให้ต้องกรอก LINE Token ซ้ำถึง 20 ครั้ง และหากเปลี่ยนเวรต้องตามแก้ 20 จุด การผูกที่ระดับ Group ช่วยให้ตั้งค่าที่เดียวควบคุมได้ทั้งตึก และ 1 ตึกยังสามารถผูกได้หลายกลุ่มแชท (เช่น แชทพยาบาลเวร + แชทผู้บริหาร)

3 ทำไมต้องมีทั้ง Surrogate Key (`id`) และ Natural Key (`device_id`)?

ตอบ: เพื่อแก้ปัญหา Hardware Replacement Decoupling ครับ ในงาน IoT หากกล่องวงจรฮาร์ดแวร์ชำรุดแล้วช่างเปลี่ยนบอร์ดใหม่ที่มี Serial ใหม่ การใช้ Integer `id` เป็น Foreign Key อ้างอิงในตารางประวัติ (device_events) นับหมื่นรายการ ทำให้เราสามารถเปลี่ยน `device_id` หรืออัปเดตเครื่องได้โดยไม่ทำให้ประวัติเหตุการณ์ในอดีตหลุดหรือพังทลายครับ

4 ทำไมฟิลด์ `metadata` ในตาราง `device_events` ต้องใช้ชนิด `JSONB`?

ตอบ: เป็นการใช้สถาปัตยกรรมแบบ Hybrid Relational-Document Model ครับ ข้อมูลสำคัญที่ต้อง Search/Sort เช่น เวลาและสถานะ เราแยกเป็นคอลัมน์มาตรฐาน ส่วนข้อมูลเทคนิคเซนเซอร์เรดาร์ (เช่น พิกัด X, Y, Z, Signal Quality, ความเร็ว) เราเก็บลง `JSONB` ซึ่งใน PostgreSQL เป็น Binary Format ที่สามารถทำ Index ค้นหาข้างในได้ และรองรับการต่อยอดเซนเซอร์รุ่นใหม่ในอนาคตโดยไม่ต้องรัน Migration แก้โครงสร้างตาราง

5 ทำไมต้องเปิดใช้ Soft Delete (`deleted_at`) ในทุกตาราง?

ตอบ: เพื่อปฏิบัติตามมาตรฐาน Healthcare & Safety Compliance ครับ ในระบบแจ้งเหตุฉุกเฉินและโรงพยาบาล ข้อมูลการเกิดอุบัติเหตุห้ามสูญหายเด็ดขาด หากผู้ดูแลเผลอกดลบห้องน้ำหรืออาคาร การลบแบบ Hard Delete จะทำให้ประวัติคนล้มในอดีตถูกล้างทิ้งไปด้วย Soft Delete จะซ่อนข้อมูลจากหน้าจอปกติ แต่ยังคงข้อมูลจริงไว้ในดิสก์เพื่อใช้เป็นหลักฐานทางการแพทย์และคดีความได้เสมอครับ

6 ทำไมเลือกใช้ PostgreSQL บน Azure Flexible Server แทน SQLite หรือ NoSQL?

ตอบ: SQLite ไม่รองรับ Concurrency การเขียนพร้อมกันจากอุปกรณ์นับร้อย และไม่รองรับการทำงานแบบคลาวด์ ส่วน NoSQL (เช่น MongoDB) ขาดการตรวจสอบ Referential Integrity (Foreign Key) ที่เข้มงวด PostgreSQL เป็น Relational DB ที่สมบูรณ์แบบ มีคุณสมบัติ ACID แท้จริง รองรับ JSONB และบน Azure Flexible Server ยังบังคับใช้ SSL Mode Require เข้ารหัสข้อมูลระหว่างส่ง 100% ป้องกันการดักดมข้อมูลในเครือข่ายครับ

func (s *Service) ProcessEvent(devID, evType, name, val, meta string) error {
    // 1. ตรวจสอบว่าถ้าเป็น fall หรือ prolonged_stay ให้ตั้งสถานะเป็น "pending" เพื่อรอคนช่วย
    status := "normal"
    if name == "fall" || name == "prolonged_stay" {
        status = "pending"
    }

    // 2. บันทึกเหตุการณ์ลงตาราง device_events
    event := iot.DeviceEvent{
        DeviceID: dev.ID,
        Type:     evType,
        Name:     name,
        Value:    val,
        Metadata: meta,
        Status:   status,
    }
    s.db.Create(&event)

    // 3. ยิงแจ้งเตือน LINE แบบ Asynchronous (Goroutine) เพื่อไม่บล็อกการตอบสนอง
    if name == "fall" {
        msg := fmt.Sprintf("🚨 [แจ้งเตือนเหตุฉุกเฉิน: ตรวจพบคนหกล้ม!]\n📍 อาคาร: %s\n🚪 ห้อง: %s", group.Name, dev.Name)
        for _, cfg := range configs {
            go notifier.SendLineNotification(cfg.Type, cfg.LineToken, cfg.LineGroupID, msg)
        }
    } else if name == "prolonged_stay" {
        msg := fmt.Sprintf("⏳ [แจ้งเตือน: เข้าห้องน้ำนานเกินกำหนด]\n📍 อาคาร: %s\n🚪 ห้อง: %s", group.Name, dev.Name)
        for _, cfg := range configs {
            go notifier.SendLineNotification(cfg.Type, cfg.LineToken, cfg.LineGroupID, msg)
        }
    }

    // 4. กระจายข้อมูลสดเข้า WebSocket Hub ไปยังทุกหน้าจอของเจ้าหน้าที่
    s.hub.Broadcast(wsPayload)
    return nil
}

คลังคำถาม-คำตอบเพื่อการสอบจบ (Master Defense Q&A Cheat Sheet)

10 คำถามยอดฮิตที่คณะกรรมการมักจะถาม พร้อมคำอธิบายเชิงวิศวกรรมที่ถูกต้องและน่าเชื่อถือที่สุด

1 ทำไมถึงเลือกใช้เรดาร์คลื่นมิลลิเมตร (mmWave) แทนการใช้กล้อง AI หรือเซนเซอร์อื่นๆ?
แนวทางตอบ: ห้องน้ำเป็นพื้นที่ส่วนบุคคลสูงสุด มีข้อจำกัดทางกฎหมายคุ้มครองข้อมูลส่วนบุคคล (PDPA/Privacy Law) ที่ห้ามติดตั้งกล้องถ่ายภาพทุกชนิด ส่วนเซนเซอร์อินฟราเรด (PIR) ตรวจจับได้เฉพาะการขยับตัว หากผู้สูงอายุล้มหมดสติหรือนอนนิ่ง PIR จะเข้าใจว่าห้องว่าง อีกทั้งความชื้นและไอฝ้าจากฝักบัวยังบดบังเซนเซอร์แสง เรดาร์คลื่นมิลลิเมตรจึงเป็นคำตอบที่สมบูรณ์แบบที่สุด เพราะส่งคลื่นสะท้อนวัตถุ ไม่สร้างภาพถ่าย ทำงานได้แม้ในที่มืดสนิท (0 Lux) และทะลุละอองน้ำไอน้ำได้ 100% ครับ
2 ทำไมต้องใช้เรดาร์ 2 ตัว (LD6002C 60GHz และ LD2410C 24GHz) ทำไมไม่ใช้ตัวเดียวเพื่อประหยัดต้นทุน?
แนวทางตอบ: เพื่อทำ Sensor Fusion ข้ามย่านความถี่ แก้ปัญหา False Alarm ครับ เรดาร์ 60GHz มีความแม่นยำสูงมากในการจับพลวัตการตกกระทบ (Impact Velocity) แต่มักสับสนเมื่อมีสิ่งของ เช่น ขวดแชมพูหรือผ้าเช็ดตัวขนาดใหญ่ร่วงหล่น การนำเรดาร์ 24GHz (LD2410C) มาทำหน้าที่เป็น Empty Room Guard จะช่วยยืนยันว่ามีมนุษย์อยู่ในห้องจริงก่อนที่จะยอมรับเหตุการณ์ล้ม ทำให้ระบบไม่เกิด False Alarm รบกวนเจ้าหน้าที่ และ LD2410C ยังจับการหายใจของคนหมดสติได้นิ่งกว่าด้วยครับ
3 ถ้าเกิดไฟดับ สายไฟหลุด หรือตัวบอร์ดพัง ระบบจะทราบได้อย่างไรว่ากล่องนั้น "ออฟไลน์" ในเมื่อเครื่องดับไปแล้ว?
แนวทางตอบ: เราใช้มาตรฐานสากลของ IoT คือ MQTT Last Will and Testament (LWT หรือพินัยกรรม) ครับ ตอนที่ตัวบอร์ดเชื่อมต่อเน็ตเข้ากับ Broker จะฝากข้อความพินัยกรรม {"name":"offline"} ไว้ล่วงหน้า หากบอร์ดดับกะทันหันจนสัญญาณขาดหายไปโดยไม่บอกลา ตัวโบรกเกอร์ (Mosquitto) จะเป็นผู้เปิดพินัยกรรมและส่งข้อความ offline ให้กับระบบหลังบ้านแทนตัวบอร์ดทันที หน้าจอแดชบอร์ดจึงเปลี่ยนสถานะเป็นการ์ดสีเทาได้ทันทีโดยไม่ต้องรอครับ
4 ถ้าผู้สูงอายุแค่ขับถ่ายนาน หรือท้องผูก ระบบจะส่งเสียงไซเรนดังลั่นทำให้เขาตกใจหรืออับอายหรือไม่?
แนวทางตอบ: ไม่ดังครับ! ระบบของเราแยกลำดับความรุนแรงของเหตุการณ์ชัดเจน:
  • คนล้มฉุกเฉิน (fall): ไซเรนจะเปิดทันทีเพื่อขอความช่วยเหลือเร่งด่วน
  • อยู่นานเกินกำหนด (prolonged_stay): ไซเรนจะ ไม่ทำงานเด็ดขาด (Silent Alert) แต่จะแสดงไฟสีส้มที่ตัวเครื่อง และส่งข้อความเงียบเข้า LINE ของผู้ดูแล เพื่อให้พยาบาลเดินมาเคาะประตูถามไถ่อย่างสุภาพ ไม่ละเมิดศักดิ์ศรีและไม่สร้างความตกใจให้ผู้สูงอายุครับ
5 ถ้าระบบติดตั้งในโรงพยาบาลหรือคอนโดที่มี 50 - 100 ห้องน้ำ เซิร์ฟเวอร์จะรับโหลดไหวไหม ข้อมูลจะชนกันหรือไม่?
แนวทางตอบ: รับได้สบายมากครับ เพราะระบบถูกออกแบบด้วยสถาปัตยกรรม Microservices:
  1. MQTT Protocol: เป็น Publish/Subscribe ที่เบามาก แพ็กเก็ตมีขนาดเล็กระดับร้อยไบต์ โบรกเกอร์ Mosquitto รับ Concurrency ได้ระดับหมื่นอุปกรณ์พร้อมกัน
  2. ภาษา Go (Golang): ใช้ Goroutine ในการประมวลผล แต่ละ Thread ใช้หน่วยความจำเพียง 2 KB สามารถรับส่งข้อมูลแบบ Non-blocking
  3. เราได้สร้างหน้าจำลอง simulator/index.html ที่สามารถยิง Stress Test จำลองอุปกรณ์พร้อมกันหลายๆ ห้องส่งขึ้น Azure Cloud ได้แบบสดๆ ให้กรรมการชมได้ครับ
6 ถ้าผู้สูงอายุสะดุดล้ม แต่สามารถพยุงตัวลุกขึ้นยืนเองได้ ระบบจะจัดการอย่างไร?
แนวทางตอบ: เรามีฟังก์ชัน Fall Auto-Recovery ในเฟิร์มแวร์ครับ เมื่อเกิดเหตุล้ม ระบบจะยังจับตาดูความสูงและพิกัด หากพบว่าเป้าหมายสามารถลุกขึ้นมายืนทรงตัวในระดับความสูงปกติได้ต่อเนื่องเกิน 2.5 วินาที ตัวบอร์ดจะยกเลิกสถานะล้ม ปิดเสียงไซเรน และปรับสถานะกลับมาเป็น enter (กำลังใช้งาน) โดยอัตโนมัติ ไม่รบกวนหน่วยกู้ชีพครับ
7 หากขนาดห้องน้ำหรือความสูงเพดานแต่ละห้องไม่เท่ากัน จะต้องแก้โค้ดและแกะกล่องมาแฟลชใหม่ทีละกล่องหรือไม่?
แนวทางตอบ: ไม่ต้องครับ เราทำระบบ Remote Configuration ผ่านหน้า Web Dashboard ไว้ ผู้ดูแลสามารถกดตั้งค่าความสูงเพดาน (Mount Height), ความกว้างยาวห้อง และเวลาอยู่นานเกิน ผ่านหน้าเว็บได้เลย ข้อมูลจะวิ่งผ่าน MQTT เข้าสู่บอร์ด และบันทึกลง NVS Flash Memory ของ ESP32 อัตโนมัติ แม้ไฟดับค่าคอนฟิกก็ไม่หายครับ
8 ถ้าอินเทอร์เน็ตของอาคารล่ม หรือ Wi-Fi ขาดหาย ตัวอุปกรณ์ยังสามารถช่วยชีวิตคนได้อยู่หรือไม่?
แนวทางตอบ: ยังทำงานได้ในระดับ Local ครับ เพราะระบบออกแบบสถาปัตยกรรมแบบ Edge Computing สมองกลและตรรกะการตรวจจับการล้มทำงานอยู่บนตัวชิป ESP32-S3 โดยตรง หากเน็ตตัด ไซเรนแจ้งเตือนฉุกเฉินและไฟกะพริบสีแดงหน้าห้องน้ำยังคงทำงานได้อย่างสมบูรณ์เพื่อแจ้งคนบริเวณใกล้เคียง และเมื่อเน็ตกลับมาต่อติด บอร์ดจะส่งข้อมูลย้อนหลังขึ้นสู่เซิร์ฟเวอร์ครับ
9 การบันทึกประวัติ (History Log) มีประโยชน์อย่างไรในทางการแพทย์ และมีขั้นตอนจัดการอย่างไร?
แนวทางตอบ: มีประโยชน์อย่างมากในด้าน Clinical Audit & Response Time ครับ ระบบบันทึกเวลาที่เกิดเหตุ (Triggered Time), เวลาที่เจ้าหน้าที่เข้าถึงตัว (Resolved Time), ผู้เข้าช่วยเหลือ (Resolved By) และบันทึกอาการ (Note) ข้อมูลนี้ช่วยให้แพทย์ทราบว่าคนไข้นอนหมดสตินานกี่นาทีเพื่อวินิจฉัยภาวะกล้ามเนื้อสลาย (Rhabdomyolysis) และช่วยให้ผู้บริหารตรวจสอบ KPI เวลาการเข้าช่วยของเวรพยาบาลได้ครับ
10 โครงสร้างระบบมีความปลอดภัยทางไซเบอร์ (Cybersecurity) อย่างไรบ้าง?
แนวทางตอบ: เราออกแบบความปลอดภัยระดับ Enterprise:
  1. การเชื่อมต่อเว็บและ WebSocket ทั้งหมดผ่าน HTTPS/WSS เข้ารหัส TLS/SSL ด้วยใบรับรอง Let's Encrypt
  2. ฐานข้อมูล PostgreSQL บน Azure บังคับใช้การเชื่อมต่อแบบ SSL Mode Require และปิดพอร์ตไม่ให้คนภายนอกเข้าโดยตรง
  3. รหัสผ่านผู้ดูแลระบบถูกเข้ารหัสด้วย Bcrypt Hash พร้อม Salt ไม่มีทางถอดรหัสเป็นข้อความธรรมดาได้
  4. ระบบรันบน Docker Private Network ปิดกั้นพอร์ตที่ไม่จำเป็นทั้งหมดครับ
